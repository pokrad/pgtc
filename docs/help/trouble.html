Troubleshooting

Key combinations the terminal does not deliver, rendering problems, connection and authentication errors with their server-side cause, frequent questions, and the log file.

If a key does not work

pgtc receives only the key events the terminal emulator delivers. Every terminal reserves some combinations for itself — switching its own tabs, scrolling, changing the input method — and the legacy terminal protocol cannot encode others at all (Ctrl+Enter and Enter are the same byte).

Three workarounds always apply:

  1. Use the alternative binding. The commands usually affected have one — see the table.
  2. Use the menu. F9 (or Esc 9) reaches nearly every command.
  3. Rebind the command in keymap.toml.

Terminals that deliver every key. Terminals with the kitty keyboard protocol — kitty, WezTerm, foot, Ghostty, recent Alacritty, iTerm2 when it is enabled — report all of these combinations unambiguously; pgtc enables the protocol at start. PuTTY

Alt + arrows work with PuTTY's default settings. In PuTTY 0.77 and newer you can also choose Terminal → Keyboard → Arrow keys with modifiers: xterm-style.

Finding out what a key does

Press F1: if the key is listed but pressing it does nothing — or something else — the terminal intercepts or alters it. If it is not listed, the command is not available in the focused part.

Questions and answers

“New query” and “Open SQL file” are disabled

A query tab is a session on one database. Put the tree cursor on a database — or on any object inside one — on a connected server. A server row, a role and a tablespace are cluster-wide: they name no database to connect to.

F7 says “No developer templates”

The templates are not installed yet: Settings → Install templates, or pgtc --setup on the command line.

F7, F4 or autocomplete say I should finish or close the result first

The tab has a paused result — its label shows 1,000+ rows — or an export is running. The statement is still in progress on the tab's session: the backend has not sent all rows yet, and a session executes one statement at a time, so the catalog queries these commands need cannot run. Press Alt+End to fetch the remaining rows, or Alt+Shift+C to close the result; then try again. See Large results.

A statement says it “cannot run inside a transaction block”

SQLSTATE 25001. pgtc sends the script as one simple-protocol Query message, and the server runs a multi-statement message as an implicit transaction block. VACUUM, CREATE DATABASE, CREATE INDEX CONCURRENTLY, ALTER SYSTEM and a few others must run outside any transaction block. Select that statement alone and press F5 — with Auto commit on, since with it off pgtc sends BEGIN first.

My script failed in the middle. What was changed?

Nothing — unless the script contains its own COMMITs. The statements of one Query message form an implicit transaction block: on the first error the server rolls it back and skips the rest of the message. An explicit COMMIT inside the script makes everything before it durable. Fix the statement the error position points to and run the script again.

Every statement answers “current transaction is aborted”

SQLSTATE 25P02: a statement failed inside a transaction block — Auto commit is off, or the script issued BEGIN — and the session is in the aborted-transaction state (the status row says Transaction failed – rollback). The server rejects everything except ROLLBACK / ROLLBACK TO SAVEPOINT. Choose Query → Rollback. To have pgtc send the ROLLBACK itself after an error, turn on Query → Auto rollback on error.

I created a table but the tree does not show it

The tree caches the catalog rows it has loaded and does not watch for DDL. Put the cursor on the schema (or on Tables) and press Ctrl+R to read them again.

Autocomplete does not offer a new table or column

Each query tab caches the names it has read from the catalogs. The cache is dropped after that tab executes a CREATE / ALTER / DROP, and after a refresh of the tree (Ctrl+R there). DDL executed in another tab or by another session is not noticed: refresh the tree.

Copy does not reach my clipboard over SSH

Over SSH the text reaches the local clipboard through the terminal, as an OSC 52 escape sequence. The terminal must support it and allow it — Windows Terminal, iTerm2, kitty, WezTerm and Alacritty do; in some it is a setting (iTerm2: Applications in terminal may access clipboard; tmux: set -g set-clipboard on). In pgtc, OSC 52 clipboard must be on in Settings. If your terminal cannot do it, select the text with the terminal itself: hold Shift and drag.

Paste with Ctrl+V pastes something old (over SSH)

Over SSH, Ctrl+V reads the clipboard of the remote host or pgtc's internal buffer. To paste from the local clipboard, use the terminal's paste: Ctrl+Shift+V, Shift+Insert or the right mouse button.

Where did my exported file go?

To the host pgtc runs on — the export is written client-side by pgtc, not by the server (it is not COPY … TO a server file) — into the folder shown in the dialog's Folder: line. Over SSH that is the remote host; fetch the file with scp or sftp.

I cannot select text with the mouse to copy it out of the terminal

pgtc enables mouse reporting. Hold Shift while dragging and the terminal does its own selection.

A SQL file does not open because it is not UTF-8

pgtc reads SQL files as UTF-8. Convert the file, for example: iconv -f WINDOWS-1250 -t UTF-8 old.sql > new.sql.

The profiler does not start

  • logging_collector is off — the profiler reads the server log through SQL, which requires the logging collector. Set logging_collector = on (postgresql.conf or ALTER SYSTEM) and restart the server; pgtc does not restart servers.
  • Missing privileges — the profiler changes log_destination and log_min_duration_statement with ALTER SYSTEM and pg_reload_conf(), and reads the log file with pg_read_binary_file(). That needs a superuser, or pg_read_server_files plus the right to run ALTER SYSTEM.
  • A managed cloud service — usually neither is granted there.

See SQL profiler.

pgtc asks about “logging settings” when I connect

The profiler was running when pgtc last ended without being able to restore the logging parameters it had changed with ALTER SYSTEM; the server still logs every statement. Answer Yes to restore them. See If pgtc could not put the settings back.

The dashboard shows “-” for some values, or no query text for other sessions

pg_stat_activity and the other statistics views expose the details of other roles' sessions only to superusers and to members of pg_read_all_stats (included in pg_monitor): GRANT pg_monitor TO your_role;

Cancel or terminate in the dashboard is refused

pg_cancel_backend() and pg_terminate_backend() are permitted on backends of the calling role (and of roles it is a member of); for others the caller must be a superuser or a member of pg_signal_backend. Backends of superusers can be signalled only by superusers.

Can I change a table / drop an object with a dialog?

No — pgtc generates DDL for review instead of executing it from a dialog. To change an object: Ctrl+E on it (Edit in new query tab). To create or drop one: F7 (developer templates). To write statements for a table's rows: F4 and gti, gtu, … (generate commands).

Can I edit the rows of a result in the grid?

No. The grid is read-only. Change data with UPDATE / INSERT / DELETE; gtu table on F4 generates the UPDATE with every column.

Can I see the query plan?

Prefix the statement with EXPLAIN or EXPLAIN (ANALYZE, BUFFERS) and run it: the plan is returned as the result set. EXPLAIN ANALYZE executes the statement — run DML with Auto commit off and roll back.

How do I move my settings to another machine?

Copy settings.toml and keymap.toml from the config folder and the themes and developer_templates folders from the data folder — see Files and folders. Passwords are in .pgpass.

The log file

pgtc writes nothing to stdout or stderr while the UI is active. Diagnostics go to a log file, rotated daily, in the logs folder of its data folder:

PlatformLog folder
Linux~/.local/share/pgtc/logs
macOS~/Library/Application Support/pgtc/logs
Windows%APPDATA%\pgtc\logs

The files are named pgtc.2026-11-16.log; the last 7 are kept. The default level is info. For a reproducible problem, raise the level and read the end of today's file:

PGTC_LOG=debug pgtc                 Linux, macOS
$env:PGTC_LOG="debug"; pgtc         Windows PowerShell
set PGTC_LOG=debug && pgtc          Windows cmd

PGTC_LOG=pgc_db=trace sets trace for the database layer (the pgc_db crate) only.
